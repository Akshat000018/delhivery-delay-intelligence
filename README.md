# Delhivery Last-Mile Delay Intelligence Pipeline

Capstone project, AI & ML Certification Program, E&ICT Academy, IIT Roorkee.

One connected pipeline that answers three questions for a regional operations head:

1. **How long will a parcel really take?** (regression, Part B)
2. **Which parcels will miss their promise?** (classification + alert threshold, Part C)
3. **Which hubs need which playbook?** (K-Means hub segments, Part D)

A final script, `predict_delay.py`, combines the classifier and the hub segments to turn 48 new parcels into an action list.

> The data is synthetic, produced by `generate_data.py`. Delhivery's real shipment records are never used; the brand is only the setting. Money is in Indian Rupees (INR).

## How to run

From a fresh clone of the `main` branch, in this order:

```bash
pip install -r requirements.txt
python generate_data.py          # prints: 24 1224 48
python part_a_clean_eda.py       # writes data/modelling_table.csv, part_a_*.csv
python part_b_regression.py
python part_c_classification.py
python part_d_segments.py        # hub profile, K-Means segments, tier check
python package_model.py          # regenerates models/*.pkl and the other models/ files
python predict_delay.py          # writes outputs/new_shipment_actions.csv
```

`requirements.txt` pins `pandas==3.0.6`, `numpy==2.5.4`, `scikit-learn==1.9.1` and `joblib==1.6.0`, the versions this work was run on. **`models/delay_model.pkl` is regenerated by running `python package_model.py`.** The committed pickle loads reliably only on the scikit-learn version pinned in `requirements.txt`; if your installed versions differ, re-run `package_model.py` rather than loading the committed file. Every script uses only files in the repository and the fixed `random_state` values from the brief, so a re-run reproduces every CSV (running `predict_delay.py` twice gives byte-identical output).

## Data findings

Cleaning (`clean_shipments` in `src/shipment_prep.py`): 24 duplicate rows removed from 1,224 (1,200 remain, `part_a_checks.csv`); 12 service-type spellings collapsed to 3; 5 scanner-fault weights (999) treated as missing; gaps in distance (36), weight (24) and declared value (12) filled with medians (314.95 km, 1.83 kg, INR 1,121.50); 18 missing payment modes set to "Unknown". The modelling table has 1,200 rows, no missing value in the 17 features, and 278 delayed parcels (delay rate 0.2317).

1. **Express is delayed most often.** In `part_a_delay_by_group.csv`, Express has a delay rate of 0.4897 (119 of 243 parcels), against 0.2056 for Standard and 0.0857 for Economy. Express has the tightest promise (36 hours) for the same physical journey.
2. **Delay rises steeply with hub tier.** Tier 1 is 0.0400, Tier 2 is 0.2150 and Tier 3 is 0.4400: roughly eleven times more delays at Tier 3 than at Tier 1.
3. **Delay rises even more steeply with distance.** 0-200 km: 0.0219; 201-400 km: 0.1368; 401-600 km: 0.4364; 601+ km: 0.8523. Parcels travelling more than 600 km are late far more often than not.
4. **Strongest correlations with `delivery_hours`** (`part_a_correlations.csv`, ranked by absolute value, excluding `delivery_hours` itself): `promised_hours` (+0.8372), `distance_km` (+0.4013) and `n_stops` (+0.3247). The first is partly structural, because the service type sets both the promise and the base time.
5. **Why `declared_value_inr` was log-transformed.** On the median-filled column the mean is INR 1,533.05 but the median is INR 1,121.50 (a long right tail of high-value parcels), whereas after the natural log the mean (7.0277) and median (7.0224) are almost identical, so the log column is roughly symmetric.

Outlier check: with the 1.5 x IQR rule on `delivery_hours` (bounds -0.71 and 116.52 hours) exactly 1 parcel is an outlier, so none were removed.

## Model results (regression)

All numbers from `part_b_metrics.csv`, `part_b_tree_depth.csv`, `part_b_gb_learning_rate.csv`, `part_b_cv.csv`. Split: 840 train / 180 validation / 180 test. The scaler was fitted on the training rows only: the mean of the scaled training columns is 0.0 (rounded) while the scaled test columns reach a largest absolute mean of 0.2187, so test rows were not used to fit it (`part_b_checks.csv`).

- **Baseline.** Predicting the training mean for every parcel gives validation R² of -0.0212 (RMSE 18.8552 hours). It explains none of the variation, which is the bar every real model has to clear.
- **Winner on validation.** Linear regression, RMSE 4.8912 hours (MAE 3.9222, R² 0.9313). Gradient boosting is essentially tied (RMSE 4.9165, R² 0.9306), then random forest (5.4680) and the decision tree (6.2796). The final model, scored once on the test rows, is linear regression: RMSE 4.5235 hours, R² 0.9493.
- **Bias and variance (tree depth).** Depth 1 is **high bias**: train RMSE 11.6334 and validation RMSE 12.1324 are both high with a small gap of 0.4990, so the model is too simple. With no depth limit the tree is **high variance**: train RMSE 0.0000 against validation RMSE 7.7890 (gap 7.7890); depth 12 shows the same pattern (gap 6.0560). The sweet spot is depth 6, where validation RMSE is lowest (6.2796); beyond it the training error keeps falling while the validation error rises.
- **Learning rate (gradient boosting, 100 trees).** 0.1 is best (validation R² 0.9306). 0.01 is **too slow**: 100 tiny steps cannot reach the target (R² 0.7127). 1.0 **overshoots**: each tree over-corrects the previous one and the fit is unstable (R² 0.8440).
- **Cross-validation disagrees with validation, narrowly.** On the 1,020 training-plus-validation rows with one shared 5-fold object, gradient boosting scores a mean R² of 0.9352 (std 0.0044) against 0.9261 (std 0.0048) for linear regression. The validation gap was only 0.0253 hours of RMSE on 180 rows, which is within noise, while cross-validation averages five different 204-row folds. **I would ship gradient boosting**: it also wins the more reliable comparison, and the data contain interactions a linear model cannot represent (for example the extra delay for Express parcels during the sale, and rain on lanes longer than 400 km). The only reason the brief's rule picked linear regression is a 0.0253-hour validation edge.

## Model results (classification)

Numbers from `part_c_*.csv`. Stratified split 840 / 180 / 180 with 195 / 42 / 41 delayed parcels.

- **Blind baseline.** Predicting "on time" for every parcel gives validation accuracy 0.7667, which looks respectable, but it catches 0 of the 42 delayed parcels (recall 0.0000). It is useless for the job, which is why accuracy alone is not the metric. All three trained models reach accuracy between 0.8833 and 0.9056 and F1 between 0.7470 and 0.8046 (logistic regression 0.8046, depth-6 tree 0.7470, default forest 0.7848).
- **Noise columns.** The five bookkeeping columns carry a combined 0.2245 of the default forest's importance, even though they hold no signal (the forest splits on them to memorise training noise, so importance alone cannot be trusted). By F-score all five fall outside the top 7 (F-ranks 8, 12, 14, 16 and 17, F-scores at most 4.5847), whereas the seven real signal columns, in rank order `distance_km`, `hub_tier`, `hub_daily_capacity`, `n_stops`, `promised_hours`, `rain_flag`, `sale_event_flag`, all score above 36 (the weakest is 36.7281).
- **Choosing k** (`part_c_selectk.csv`). Validation F1 is 0.6988 at k=5 (two real signal columns are dropped), peaks at 0.8333 at k=7 (exactly the seven signal columns), then falls to 0.7857 (k=10), 0.8049 (k=12) and 0.7848 (k=17) as noise columns come back in. So k=7 was used from there on. The differences between the larger k values are small and a few parcels can move F1 on a 42-delay validation set.
- **Tuning did not help.** Grid search (27 candidates, 135 fits) reached a best cross-validated accuracy of 0.8952 and randomized search (9 candidates, 45 fits) 0.8905, but on validation their forests scored F1 0.7750 and 0.7848, below the untuned forest on the same 7 columns (0.8333). Both searches optimise accuracy, not F1, and the differences amount to a few parcels out of 42 delayed validation rows, so tuning on such a small validation set mostly chases noise. The final configuration is therefore the untuned forest (`n_estimators` 100, no depth limit, `min_samples_leaf` 1), as recorded in `part_c_final_config.csv`.
- **Alert threshold.** Validation recall of the final model is 0.9762 at 0.1, 0.8810 at 0.4, 0.8333 at 0.5 and 0.7619 at 0.6 (`part_c_thresholds.csv`). The operations rule is "highest threshold with recall of at least 0.80", so the chosen threshold is **0.5**: at that point validation precision is 0.7955 (35 true alerts and 9 unnecessary calls) with recall 0.8333 (7 delayed parcels missed). Going down to 0.4 would catch 2 more parcels but lowers precision to 0.7400.
- **Test result (scored once at 0.5).** Precision 0.6889, recall 0.7561, F1 0.7209, accuracy 0.8667 (TP 31, FP 14, FN 10, TN 125). Recall is lower than on validation (0.8333): the model caught 31 of 41 delayed test parcels against 35 of 42 on validation. With only 41 delayed parcels in the test set that is a gap of a few parcels, so it is consistent with ordinary sampling noise, but it also means the 0.80 validation recall was probably slightly optimistic, because the threshold and the configuration were both picked on that same validation set. The honest expectation for new parcels is recall of roughly three quarters, not 0.83.

## Operations recommendation

**Escalate segment.** Nine hubs make up the Escalate segment, with a mean delay rate of 0.4600 (mean delivery time 64.65 hours, mean lane distance 470.48 km, 84.34 stops per route): HUB13 Nagpur (0.4600), HUB15 Kochi (0.3600), HUB17 Patna (0.4600), HUB18 Ranchi (0.3800), HUB19 Guwahati (0.6200), HUB20 Raipur (0.4800), HUB21 Bhubaneswar (0.4000), HUB23 Siliguri (0.4400) and HUB24 Agartala (0.5400). The Watch segment has 8 hubs (delay rate 0.1550) and the Standard segment 7 hubs (0.0257). Hub-level figures are in `hub_profile.csv`, `hub_segments.csv` and `segment_profile.csv`.

**Tier labels that mislead** (`tier_vs_segment_mismatch.csv`). Four hubs behave differently from their tier label:

- **HUB07 Kolkata** (Tier 1) runs as **Watch** (delay rate 0.1400), not like a metro hub.
- **HUB13 Nagpur** (Tier 2) runs as **Escalate** (0.4600).
- **HUB15 Kochi** (Tier 2) runs as **Escalate** (0.3600).
- **HUB22 Dehradun** (Tier 3) runs as **Watch** (0.2000), better than its label suggests.

The tier is a size and capacity label, not a measure of operating behaviour. It should not be used to pick a playbook: use the observed segment for that, and keep the tier only as a descriptive attribute (it is still a useful model input, being the second-ranked feature by F-score).

**Alert rule.** Flag a parcel when its predicted delay probability is at least **0.5**. On the held-out test rows this means about **6.9 of every 10 flagged parcels are really delayed** (precision 0.6889) and about **7.6 of every 10 delayed parcels are caught** (recall 0.7561). The remaining flags are unnecessary calls, which the business has judged cheaper than a missed delay.

**New parcels.** Of the 48 parcels in `new_shipments.csv`, **8 are flagged**, and **6 of those need a hub-manager escalation** because they are dispatched from Escalate hubs; the other 2 get a proactive customer call (`new_shipment_actions.csv`). The remaining 40 need no action.

**Why K = 3 and not more** (`part_d_separation.csv`). The across-to-within distance ratio is 2.8940 for K=2 and jumps to 5.3928 for K=3 (sizes 9-8-7), the largest gain; it keeps rising only slowly to 6.3047 for K=4 and 6.8866 for K=5. Those higher-K solutions (sizes 8-7-5-4 and 8-7-4-3-2) contain clusters of fewer than 6 hubs, too small to carry their own playbook, and operations runs exactly three playbooks, so K=3 is kept.

## Production plan

**(a) Production-readiness characteristics mapped to this repository**

| Characteristic | Where it lives |
|---|---|
| Accuracy | Held-out evaluation with a test set scored once (`part_c_final_test.csv`: recall 0.7561, precision 0.6889), plus the cross-validation in `part_b_cv.csv`. |
| Reliability | `clean_shipments` handles duplicates, casing, sentinels and gaps; `part_a_checks.csv` shows 0 nulls in the features and target; `new_shipments.csv` is scored with the stored medians and never fails on missing values. |
| Reproducibility | Fixed `random_state` everywhere, pinned `requirements.txt`, committed generator, deterministic scripts run in a documented order, byte-identical output on two runs of `predict_delay.py`. |
| Performance (speed) | A 100-tree forest on 7 selected features: scoring 48 parcels is a single `predict_proba` call; the whole pipeline runs in seconds on a laptop. |
| Maintainability | One shared `src/shipment_prep.py`, constants (`FEATURES`, `PROMISED_HOURS`) in one place, one script per Part, and `package_model.py` to rebuild the model on any new scikit-learn version. |
| Consistency (same preprocessing in training and prediction) | `predict_delay.py` imports `clean_shipments` and `build_features` from the same module that built the training table, applies `impute_values.csv`, and orders columns by `feature_order.csv`. |
| Monitorability | The stored threshold, the expected flag rate and the per-segment profile (`hub_profile.csv`, `segment_profile.csv`) are saved as files that live numbers can be compared against (see b). |

**(b) What to monitor, with triggers**

- **Weekly delayed share of delivered parcels.** The training rate is 0.2317. Investigate if the weekly rate moves more than 5 percentage points away from the expected value for the same kind of week, for two weeks in a row.
- **Weekly share of parcels flagged.** At threshold 0.5 the flag rate was 0.2444 on validation (44 of 180) and 0.2500 on test (45 of 180). Alert if the weekly flagged share leaves the 0.15 to 0.35 band.
- **Recall on parcels whose outcome is now known.** Measured over a rolling four weeks (at least 30 delayed parcels so it is not noise). Test recall was 0.7561; trigger a review if it falls below 0.65.
- **Input drift.** Weekly mean `distance_km` and `n_stops`, share of "Unknown" payment modes, and count of sentinel weights; trigger when any moves more than 15% from its training value.

**(c) Retraining and the sale window.** Retrain monthly on the latest delivered parcels (re-running the same scripts and `package_model.py`) and immediately when a trigger above fires. The 15-28 September sale (`sale_event_flag`) lifts delivery hours (more so for Express), so a high delay rate in that window is expected and must not be compared with ordinary weeks. Compare it with the same kind of event, that is with the previous sale window, and include sale-period parcels in the retraining data well before the next sale. Data drift here would look like: a change in the mix of hubs, lanes or service types (for example longer average distance or more Express parcels), hubs migrating between segments (re-cluster each quarter and re-check `tier_vs_segment_mismatch.csv`), new hubs that have no history, or the delay rate rising while the inputs look unchanged (concept drift, such as new carrier or road conditions).

## Limitations

- **Synthetic data.** Delays were generated by a formula with Gaussian noise and four planted "mismatched" hubs; real logistics data has weaker, messier signal, so every metric here is optimistic.
- **Few delayed parcels in the test set.** Only 41 delayed parcels (and 42 in validation) back the recall, precision and threshold estimates; a few parcels more or fewer would move them noticeably.
- **Threshold and configuration tuned on one validation split.** The 0.5 threshold, k=7 and the choice among three forest configurations were all picked on the same 180 rows, so the validation recall (0.8333) is optimistic compared with test recall (0.7561). A cross-validated threshold would be more stable.
- **Availability of features at dispatch time.** `rain_flag` and `n_stops` are used as if known at dispatch; in production rain would have to come from a forecast and the route plan from the planning system, which would make the inputs noisier than in this historical data.
- **Segments use all history.** Hub segments are computed from all 1,200 historical parcels (including those later used for validation and test), over a single 90-day window with one sale event, so they ignore seasonality and should be refreshed regularly.
- **Pickle portability.** `delay_model.pkl` can only be loaded safely by the scikit-learn version that wrote it; `package_model.py` must be re-run after any upgrade.
